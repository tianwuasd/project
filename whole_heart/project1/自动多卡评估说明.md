# 自动多卡评估（最多三张卡）

2026-09-28 新增。只调整最终评估的任务调度，沿用现有模型、病例划分、滑窗预测、Dice/HD/HD95 和后处理规则。不是把单个模型拆到三张卡上，而是一张卡评价一个模型，完成后领取下一个模型。

## 新手使用

**已经在服务器上运行的旧评价不会自动切换。不要在它运行时覆盖代码、再启动一套评价或删除旧记录。**

新版本同步到服务器、确认原来的任务已退出后，在 project1 目录运行：

```bash
bash run_zmic44.sh --mode evaluate
```

按提示填写或回车沿用三个路径，输入 RUN。此模式不再要求手动填写显卡编号；后台等待并检测空闲卡。也可以在交互菜单选择 **4：十次训练已完成，仅继续评价**。

以后用新版本启动完整实验时，十次训练结束会自动进入多卡评价。已有旧版本训练完成的工作区请选评价模式，不要选重新运行完整实验：旧训练的续跑校验仍保持严格。

## 怎样判定空闲

配置文件：`06_configs/evaluation_gpu.json`。这是本项目的保守默认值，不是 NVIDIA 的统一标准，也不是对显存绝对够用的保证。

| 配置项 | 默认值 | 含义 |
|---|---:|---|
| max_gpus | 3 | 最多三张，可改为 1 或 2 |
| min_free_mib | 8192 | 剩余显存至少 8 GiB；保留推理余量，不修改训练规划预算 |
| max_utilization_percent | 10 | 利用率不得超过 10% |
| idle_samples | 3 | 连续三次全部通过 |
| sample_interval_seconds | 2 | 采样间隔两秒，初次判断至少跨四秒 |
| retry_seconds | 30 | 没有卡时三十秒后重试 |
| allowed_gpus | null | 自动探测当前分配范围中的卡；可设为 `["2", "3", "4"]` 进一步缩小范围 |

还必须满足：**没有任何计算进程**。即使利用率是 0%、显存还有很多，只要有计算进程就跳过。因为这个进程可能正在等CPU或磁盘数据，很快还会继续用GPU。查询失败、字段不可解析或无法识别系统分配编号时停止并报错，不把“不知道”当成“空闲”。

程序保存入口原始 CUDA_VISIBLE_DEVICES 范围，并与容器/Slurm 的可见限制以及 allowed_gpus 取交集。无法识别的特殊分配格式（例如范围语法或 MIG）会拒绝，请先配置可明确映射的编号/完整 UUID。程序不实现 Slurm 资源申请，也不能发现环境变量之外的管理员预约。

首次选出最多三张符合条件的卡，按空闲显存从多到少排序。少于三张就用实际空闲数量；选定后不自动扩充卡池。每次给已选卡派发新模型前再次多次采样检查；卡被其他任务占用就等待，不结束其他人的进程。

**检测不是资源预订。** 检测结束和任务启动之间仍有竞争窗口；共享服务器应遵守管理员的使用约定或通过集群调度器申请。不能保证此后没有其他用户启动任务。

## 不检查会怎样

- 只看利用率：可能撞上暂时等数据的训练任务。
- 只看剩余显存：可能两个任务挤在同一张卡上，互相拖慢。
- 不看显存：模型初始化、滑窗推理时可能显存不足退出。
- 只检查一次：启动前卡可能已被别人占用。

## 查看进展和结果

```bash
bash run_zmic44.sh --mode status
```

状态包含最终评价任务列表、运行/完成状态和GPU UUID。各模型的逐病例日志在结果目录 `08_results/evaluation/queue_logs/`；主日志会打印完整日志路径。原来主日志中的逐病例 Dice 现在在这些分模型日志里。

最终汇总仍在 `09_reports/final_evaluation/README.md`，只有全部模型评价成功才写入。任何一个模型失败，停止本次评价子进程并保留已完成病例；修复后使用同一入口续评。中断尚未写出完成记录的病例会重新计算。

## 老模型与记录兼容

`06_configs/evaluation_code_compatibility.json` 记录了已审计的旧版及本次代码完整 SHA256 清单。只对精确匹配的旧训练版本放行本次评价调度升级，保留旧训练签名和冻结清单，因而已经完成且校验通过的病例可以复用。额外代码改动、权重变化、指标协议变化、数据或环境记录不一致仍会阻止复用。不要手工编辑兼容清单来绕过校验。

推理和指标代码没有改变，GPU并发不意味着三倍加速：CPU、NAS读写和不同模型的任务长度仍会影响总耗时；不同GPU运行也不承诺浮点计算逐位相同。
