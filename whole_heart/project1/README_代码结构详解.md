## 1. 先用一句话说明项目

输入一位患者的三维 CT 或 MRI，模型给每个体素分配一个类别，最后得到七种心脏结构的三维区域。

这里的“体素”就是三维图像中的小格子。二维照片由像素组成，三维医学图像由体素组成。一个病例不是一张普通照片，而是一整份三维扫描，可以沿不同方向查看很多切片。

训练时，一个病例有两份文件：

```text
Case1001_image.nii.gz  → 扫描图像，提供模型要看的内容
Case1001_label.nii.gz  → 专家标注，提供模型学习时对照的答案
```

预测时，模型只需要图像；专家标注用于训练或评估，不是预测新患者时必须提供的输入。模型输出的是分割图，不是把原图真的切掉，也不是只给整张图一个类别。

我们的研究还要回答：**在一些医院的数据上训练后，换到另一家没参加训练的医院，模型还能不能分好？外观增强是否能改善这种跨中心表现？**

## 2. 哪些是我们写的，哪些由 nnU-Net 完成

可以把这个项目理解为：**nnU-Net 提供分割和训练的主要能力，project1 负责把研究任务组织好。**

| 部分 | 谁负责 | 通俗解释 |
|---|---|---|
| U-Net 网络的构建、主要训练步骤、优化器与损失 | 安装在环境里的 nnU-Net / PyTorch | 真正负责学习和计算的主体 |
| 数据特征统计、网络规划、重采样与归一化 | nnU-Net 官方接口，由本项目调用 | 决定图像如何准备、每次取多大块、网络怎样配置 |
| 原始标签转换、中心隔离、病例清单核对 | 本项目代码 | 决定什么数据可以进入哪项实验 |
| B0/B1 训练器与额外外观增强 | 本项目代码 | 在相同基础上安排对照方法与改进方法 |
| 启动、恢复、日志、图表与记录 | 本项目代码调用相关库 | 让实验能运行、能查错、能追溯 |

所以你没有看到一个很大的 `model.py`，不代表没有模型。网络由 nnU-Net 根据生成的 `Project1Plans.json` 构建，相关包安装在 Conda 环境里；我们没有复制整套 nnU-Net 到项目目录，也没有修改其安装目录中的源码。

本机已生成的 CT 规划使用三维 U-Net。`3d_fullres` 表示在规划的三维分辨率配置下训练，**不表示一次把患者的整个扫描都放进显卡**。

这也不是先手工提取“心脏的圆度、纹理、面积”，再把这些特征送入分类器的方案。网络会在训练中学习有用的图像特征；预处理主要负责让影像适合计算、让空间关系和标签保持正确。

### 3.2 为什么方案、实验和报告要分开

`01_protocol` 说明“原本打算怎样做”；`07_experiments` 记录“这一次实际上做了什么”；`09_reports` 解释“这些结果能说明什么”。

例如计划训练 250 轮，但实际只完成 5 轮，实验记录必须写 5 轮。不能因为方案里写了 250，就把结果描述成完整训练。

`03_workflow` 保存的是科研组织流程和角色说明。这里的 skill/agent 不是分割网络，也不会作为一层网络参加 GPU 训练。

## 4. 从一个病例走到一次训练：完整数据流

```text
原始扫描 + 专家标注
        ↓ 定位文件、核对清单和文件校验值
确认病例身份、中心、模态、是否暂时排除
        ↓ 按固定划分选择来源训练集和来源开发集
转换为 nnU-Net 的目录格式；标签改为连续的 0～7
        ↓ 只用来源训练病例统计数据特点、生成网络规划
按规划预处理来源训练病例和开发病例
        ↓ 从训练病例中抽取三维小块
执行 B0，或 B0 + 额外外观增强的 B1
        ↓ 预测、计算损失、反向传播、更新权重
定期用来源开发集检查学习情况，保存日志与检查点
        ↓ 方法和模型选择规则确定之后
后续再对留出中心做完整预测与评价
```

最后一段属于后续研究工作，当前服务器训练入口不会自动完成目标中心批量评价。

### 4.1 三份最重要的数据清单

| 文件 | 作用 | 类比 |
|---|---|---|
| [case_inventory.json](04_data/manifests/case_inventory.json) | 病例编号、图像与标注路径、模态、中心、文件 SHA256、可用状态 | 总花名册 |
| [quarantine.json](04_data/manifests/quarantine.json) | 哪 5 例暂时不参加实验，以及相关记录 | 待核实名单 |
| [splits_v1.json](04_data/manifests/splits_v1.json) | 每个方向哪些病例训练、开发、最终留出 | 固定的分班和考试名单 |

`eligible` 表示进入当前实验的合格清单，`quarantined` 表示暂时排除。这里的“隔离”通过清单实现，没有搬走或修改原始文件。

SHA256 可以理解为文件内容的校验值，用来检查文件是否与最初版本一致。重新压缩 `.nii.gz` 即使不改变体素，也可能改变文件校验值，因此服务器严格核对原始发布文件。

### 4.2 为什么训练标签是 0～7

官方编号是类别编码，没有大小顺序的医学含义。训练时改成连续编号便于模型处理，预测保存时再恢复官方编号。

| 部位 | 官方编号 | 训练编号 |
|---|---:|---:|
| 背景 | 0 | 0 |
| 左心室心肌 Myo | 205 | 1 |
| 左心房血池 LA | 420 | 2 |
| 左心室血池 LV | 500 | 3 |
| 右心房血池 RA | 550 | 4 |
| 右心室血池 RV | 600 | 5 |
| 升主动脉 AO | 820 | 6 |
| 肺动脉 PA | 850 | 7 |

七个部位再加背景，一共八个类别。代码中的八类并不是多出了一个心脏部位。

`map_labels()` 把官方编号转换成训练编号；`inverse_labels()` 做相反转换。遇到 421，程序会拒绝转换，不擅自认为它就是 420。因此目前暂时排除了含该未知标签的 Case3010。

### 4.3 原图和标注为什么必须对齐

除了数组尺寸相同，还必须对应同一位置和方向。影像中的 `affine` 空间矩阵负责把“第几个体素”映射到实际物理位置。

如果图像和标注看起来尺寸一样，但方向或位置不一致，模型就可能把错误位置当成答案。因此 `validate_geometry()` 会检查三维形状、空间矩阵有效性、图像与标注的矩阵一致性，并检查标签转换后能否还原。

## 5. train、val、target 和 holdG 分别是什么

| 名称 | 中文意思 | 能否用于学习或调参 |
|---|---|---|
| `train` | 来源医院中的训练病例 | 更新模型参数 |
| `val` | 来源医院中单独留出的开发/验证病例 | 观察训练、进行预先约定的模型选择；不更新网络参数 |
| `target` | 整个留出的目标中心 | 最后用于跨中心评价，不能反复拿来调参 |

`ct_holdG` 的意思是“CT 实验中，把 G 医院留到最后测试”，不是“拿 G 医院来训练”。

当前冻结的五个方向如下，数量以已排除问题病例后的清单为准：

| 实验名 | 来源训练例数 | 来源开发例数 | 留出目标例数 |
|---|---:|---:|---:|
| `ct_holdA` | 30 | 8 | 20 |
| `ct_holdB` | 32 | 8 | 18 |
| `ct_holdG` | 30 | 8 | 20 |
| `mr_holdCD` | 19 | 5 | 19 |
| `mr_holdE` | 15 | 4 | 24 |

同一病例可以在不同方向的独立实验中扮演不同角色；同一个方向内，三组互不重叠。每个方向会重新建立自己的模型和数据规划。

MRI 的 C&D 是已合并的来源组，不能据此声称分别验证了 C 医院和 D 医院。这里的 `target` 来自本地有标注的训练数据划分，也不等于比赛官方未公开答案的测试集。

代码中的外层 `ct_holdG` 与 nnU-Net 内部 `fold=0` 是两件事：前者表示留哪家医院，后者用于读取该方向内唯一一份固定训练/开发划分。本项目禁止它自动换成另一份随机划分。

## 6. `05_src` 中每个程序负责什么

你不需要把所有 `.py` 文件都执行一遍。很多文件是供其他程序调用的“工具箱”，有些是历史记录整理工具。

### 6.1 数据与预处理

| 文件 | 主要工作 | 读代码时先看 |
|---|---|---|
| [data_pipeline.py](05_src/data_pipeline.py) | 标签映射、冻结划分、几何检查、导出来源病例副本 | `LABELS`、`OFFICIAL`、`make_splits()`、`validate_geometry()`、`export_fold()` |
| [prepare_nnunet.py](05_src/prepare_nnunet.py) | 本机早期来源专用规划和预处理入口；也提供共享路径设置 | `configure_paths()`、`main()` |
| [server_data.py](05_src/server_data.py) | 在新服务器定位原始文件，核对哈希，重建路径清单 | `resolve_cases()`、`bind_workspace()` |
| [server_prepare.py](05_src/server_prepare.py) | 服务器逐病例准备，保存完成标记，中断后复用已有准备 | `prepare()` |

**导出后的名字变化：** 原始图像 `Case1001_image.nii.gz` 在 nnU-Net 的 `imagesTr` 中变为 `Case1001_0000.nii.gz`；`0000` 表示第一个输入通道，不是第零张切片。标签在 `labelsTr` 中命名为 `Case1001.nii.gz`。

`imagesTr` 内同时存放该方向的来源训练病例和来源开发病例，但谁真正用于训练由 `splits_final.json` 决定。目录名有 `Tr` 不代表其中每例都更新参数。目标中心不导出到这个目录。

**数据指纹是什么：** 它是体素间距、形状和强度等数据特点的统计摘要，不是身份识别指纹。网络规划器根据这些信息和显存预算产生 `Project1Plans.json`。

生成统计与规划时只用 `train`。随后用同一规划处理 `train` 和 `val`。这与“先把所有医院的数据混在一起统计，再拆分”不同，目的是减少测试信息提前影响方案。

**预处理具体做什么：** 调用 nnU-Net 的接口处理图像，例如按规划重采样和归一化。重采样涉及三维网格与体素间距；归一化涉及数值尺度。CT/MRI 的方案由模态和实际规划确定，应查看对应 `Project1Plans.json`，不是所有图像都机械除以 255。

`prepare_nnunet.py` 是早期本机入口；服务器主流程调用 `server_prepare.py`，不需要用户再手动运行两个准备入口。

### 6.2 模型与训练方法

| 文件 | 主要工作 | 读代码时先看 |
|---|---|---|
| [project_trainers.py](05_src/project_trainers.py) | 定义 `Project1B0` 和 `Project1B1`，约束划分和训练行为 | 两个类、`do_split()`、`get_training_transforms()` |
| [appearance.py](05_src/appearance.py) | 实现额外的亮度场和单调灰度变换 | `BiasField`、`MonotoneBezier` |

`class Project1B0(nnUNetTrainer)` 表示“基于官方训练器扩展”。我们保留官方训练的主要能力，只增加或改变本研究需要的部分。`super()` 的意思可以理解为“调用父类原来的实现”。

B0 的主要约定包括：CT 250 轮、MRI 300 轮；每轮 250 个训练步骤、50 个开发小块验证步骤；固定划分；检查指纹来源；关闭训练与推理的镜像翻转；发现非有限损失就停止；通过临时文件写出检查点再替换，减少中断导致文件损坏的风险。

**B0 仍有 nnU-Net 的其他常规数据增强，不是完全没有增强。** B1 继承 B0，再增加两种外观增强：

| 增强 | 通俗解释 | 当前代码参数 |
|---|---|---|
| `BiasField` | 让图像不同区域平滑地变亮或变暗 | 粗网格乘性场，幅度 0.25，应用概率 0.30 |
| `MonotoneBezier` | 改变灰度之间的映射，改变对比外观，保持单调顺序 | 1000 点查找表，应用概率 0.25 |

它们只改变图像数值，不移动器官，也不修改标签。两种增强分别随机应用，不是每个小块都执行，也不是只改变某一个类别。

B1 的假设是：训练时看到更多外观变化后，模型对医院间成像差异可能更稳健。这是要检验的假设，还没有得到本项目实验结果支持。

### 6.3 不同层次的检查与训练入口

| 文件 | 主要用途 | 是否用于证明方法好坏 |
|---|---|---|
| [check_project.py](05_src/check_project.py) | 检查病例、隔离记录、原始路径、审计/skill 哈希、文档链接和 PDF 文件头 | 否；这是资料完整性检查 |
| [gpu_probe.py](05_src/gpu_probe.py) | 对已规划的真实网络，用合成三维输入试一次训练计算 | 否；检查架构能否在 GPU 上运行及显存情况 |
| [smoke_train.py](05_src/smoke_train.py) | 用真实数据做少量训练、验证、保存和恢复；可选完整预测 | 否；检查工程流程 |
| [run_smoke_suite.py](05_src/run_smoke_suite.py) | 按顺序运行 CT/MRI × B0/B1 四组短测 | 否；四组都跑通不代表增强有效 |
| [local_preexperiment.py](05_src/local_preexperiment.py) | CT B0 固定小块拟合检查，再从头做少量轮次训练和看图 | 只观察初步学习情况，不是最终方法比较 |
| [server_train.py](05_src/server_train.py) | 按既定轮数执行一个正式 B0 或 B1 实验，并支持同一正式实验续训 | 产生后续研究所需模型，但还需完整评价 |

`check_project.py` 依赖本机原始路径和先前审计文件，不能代替服务器的数据定位入口；它还会写出检查报告。`gpu_probe.py` 也不是单纯显示显卡名称，它会执行一次合成数据训练步骤并保存记录。

**工程短测和前期训练是两种不同检查。** 短测主要看“有没有报错、保存恢复能不能用”；前期训练进一步看“模型是不是确实开始学会分割”。

### 6.4 启动、指标与汇总

| 文件 | 主要工作 | 注意事项 |
|---|---|---|

## 7. 训练时，图像到底怎样进入网络

### 7.1 整个病例与小块的关系

读取和预处理以三维病例为单位；训练通常从预处理后的病例中抽取三维小块。这样既保留立体结构，也能控制显存开销。

本机这次 CT 前期实验的规划是：

```text
patch_size = [96, 128, 128]  → 每个三维小块的尺寸
batch_size = 2              → 每次同时处理两个小块
输入张量形状示意： [2, 1, 96, 128, 128]
                   │  │   └─ 三个空间维度
                   │  └───── 一个灰度图像通道
                   └──────── 两个样本小块
```

这些尺寸来自本次 CT 规划，不保证 MRI、其他中心方向或其他显存预算也相同。训练时旋转等增强可能先取更大的临时块，再整理到网络需要的尺寸。

网络在每个位置产生背景和七种结构的类别分数，再选出类别构成预测。网络不是只看某个孤立的灰度值，而是利用周围三维结构判断这个位置属于哪里。

### 7.2 一步训练发生了什么

1. 从训练病例中取三维小块和对应标签。
2. 按 B0 或 B1 的规则处理训练输入。
3. 网络产生分割预测。
4. 用专家标签计算损失，衡量预测哪里不合适。
5. 反向传播计算参数该怎样调整，优化器更新权重。

项目沿用 nnU-Net 的 Dice 与交叉熵组合损失及深监督机制。你可以把交叉熵理解为约束每个位置的类别判断，把 Dice 项理解为关注分割区域的重叠。深监督让多个分辨率的输出都获得学习信号，所以部分代码中的 `target` 是多尺度标签列表，不是给同一病例标了多个互相冲突的答案。

这里的损失含负 Dice 项，所以日志中出现负损失不一定是错误；需要检查其定义、是否为有限数，以及实际预测。

### 7.3 一轮不等于“30 例每例看一遍”

在当前训练器里，**一轮按 250 次训练更新定义**，然后做 50 次开发小块验证。病例和小块会被抽样，不能把一轮理解成不重不漏地遍历所有患者的每个体素。

因此本次 5 轮是 `5 × 250 = 1250` 次基线参数更新。开发验证不执行参数更新，额外的完整预测也不算训练步骤。

CT 250 轮对应 62,500 次正式训练更新；MRI 300 轮对应 75,000 次。文件只有几 GB，并不表示只计算一次：同一批数据会被反复抽样、增强、前向计算和反向更新，这才是主要耗时来源。

## 8. 已完成的 CT 前期训练脚本怎么读

入口是 [local_preexperiment.py](05_src/local_preexperiment.py)。它默认只做 CT、B0、`ct_holdG`，不是一个通用的所有模态训练入口。

### 8.1 第一部分：固定小块拟合检查

从两个来源训练病例 Case1002 和 Case2001 中各取一个固定小批次。当前批量为 2，所以合计四个三维小块，交替训练 200 步。

这一阶段关闭随机增强和权重衰减，让检查集中在“模型能否学会这些固定输入”。得分仍在同一批训练小块上计算，不是未见患者成绩，也不等于整个病例已经拟合成功。

代码主要看 `new_trainer()`、`probe()`，以及 `phase = 'tiny_fixed_patch_fit'` 后面的循环。

### 8.2 第二部分：重新开始 B0 的前 5 轮

丢开刚才学到的权重，重新设置种子和初始化，使用固定划分的 30 例训练病例及 8 例来源开发病例。保留 B0 的常规训练设置。

“重新初始化”很重要：不能把先反复练过两例的模型直接当作从零开始的基线。代码记录并核对初始权重哈希，以检查两阶段确实从同样的起点开始。

这里还保留了正式 CT 的 **250 轮学习率调度**，只截取前 5 轮。它没有把学习率下降过程压缩成 5 轮，因此可以更合理地观察正式设置的早期学习过程。

脚本参数允许 1～10 轮，但当前没有继续已有前期实验的 `--resume` 接口。它不能通过改成 `--epochs 20` 来直接从已有第 5 轮续训；要做这样的实验，需要另行实现和核对恢复流程。

### 8.3 第三部分：固定两例看完整预测

在训练前、第 1 轮、第 5 轮，预测预先选定的来源开发病例 Case1001 和 Case2002。选择规则提前确定，不按哪张图好看或得分高来挑选。

`predict()` 调用 nnU-Net 的滑窗推理：用多个有重叠的小块覆盖整个扫描，合并结果，再恢复到原图网格，保存官方编号的分割图。

`plot_overlay()` 画出图像、专家标注、预测结果的对比。图中三个方向按原生数组轴显示，不保证对应统一的临床显示朝向；三张切片只帮助看错误，Dice 使用完整三维体积计算。

`build_report()` 把真实完成的步骤、曲线和指标整理成报告，即使中途失败也保留已有记录。时间预算在运行过程中检查，不是到达某一秒就强行打断 GPU 运算的实时计时器。

## 9. 一份实验目录里，各文件有什么用

可以直接打开已经完成的 [CT 前期实验目录中的报告](07_experiments/preexperiment_ct_B0_seed0_20260920_190341/预实验记录.md)。

```text
07_experiments/preexperiment_ct_B0_seed0_20260920_190341/
├─ 预先约定.md                  运行前选定的病例、步数与检查方式
├─ run.json                     状态、参数、时间、设备、划分、代码哈希
├─ code_snapshot/               这次训练实际使用的代码副本
├─ pip_freeze.txt               当时的软件包版本
├─ console.log                  实际运行输出
├─ tiny_fit/                    固定小块检查的模型与日志
├─ baseline/                    重新初始化后的 B0 模型、规划和日志
├─ preview_epoch000/            训练前的完整预测和对比图
├─ preview_epoch001/            第 1 轮的完整预测和对比图
├─ preview_epoch005/            第 5 轮的完整预测和对比图
├─ volume_dice.csv              每例每类的完整体积 Dice
├─ learning_curves.png          学习过程曲线
├─ 预实验记录.md                方便阅读的结果说明
├─ output_verification.json     对输出一致性的核验记录
└─ figure_render_record.json    训练完成后仅修复绘图的记录
```

目录名字中的 `ct` 是模态，`B0` 是方法，`seed0` 是随机种子，最后是运行时间。`run.json` 是这次实验的说明书，不是模型权重。

保存 `code_snapshot` 是为了防止将来改了代码之后，说不清旧结果由哪个版本生成。这次确实发生过一个例子：训练结束后修复了图例字体遮挡，只重新画图，没有重新训练，也没有改变分数。原始训练快照与当前绘图代码的差异已经单独记录。

实验目录中的 `verify_results.py`、`rerender_results.py` 属于本机历史核验/重绘脚本，含当时的绝对路径。原核验脚本还断言当前代码与当时哈希一致，因此绘图修复后直接重跑会触发该断言。它们不是跨机器通用启动入口；不要为了让它们通过而改写旧实验记录。

### 9.1 三种 Dice 不要混在一起

| 分数 | 用什么计算 | 能说明什么 |
|---|---|---|
| 固定训练块 Dice | 反复训练过的几个小块 | 能否学会这些固定样本 |
| 开发小块 Pseudo Dice | 训练过程中抽样的开发小块，按实现汇总 | 学习过程的近似趋势 |
| 完整病例 Dice | 一例患者完整三维预测和标注 | 该病例完整分割的重叠程度 |

Dice 越接近 1，重叠越好。其公式是 `2 × 预测与标注的重叠体素数 /（预测体素数 + 标注体素数）`，不是把所有背景体素也算进去的分类正确率。

前期报告是每例七个结构 Dice 的简单平均；双方都缺失某类时记录为空并在均值中跳过，不能假装该类满分。这与比赛按体积加权的 WHS 指标不同。

### 9.2 HD 和 HD95 在哪里

`metrics.py` 提供 `binary_metrics()`，对一个结构的预测和参考掩膜计算 Dice、最大 Hausdorff 距离 HD，以及 HD95。边界点通过完整空间矩阵转换到毫米坐标；距离越小越好。代码中的 HD95 定义为两个方向 95 分位距离中的较大者。

一方为空、另一方非空时，Dice 为 0，距离记为无穷并记录状态；双方都为空时记为空值。以后汇总必须保留这些失败/缺失情况，不能悄悄删除来抬高成绩。

**有指标函数不等于已经完成正式评估。** 当前 CT 前期报告只计算 Dice，没有计算 HD/HD95，没有实现官方大血管长度截断，也没有完成目标中心的批量统计。

## 10. 服务器入口怎样把这些文件串起来

```text
start_server.sh
  ├─ 检查 Linux、Conda、NVIDIA 驱动工具
  ├─ 按 environment_server.yml 创建独立环境
  ├─ 安装指定 PyTorch / nnU-Net 版本并检查依赖
  └─ server_launch.py
       ├─ 读菜单、数据路径、工作目录
       ├─ server_data.py：重新定位并校验 106 例
       ├─ 检查实际 GPU 计算与依赖版本，保存环境记录
       ├─ server_prepare.py：为所选方向准备来源数据
       └─ 根据任务选择
            ├─ 短测：run_smoke_suite.py → summarize_smoke.py
            └─ 正式：server_train.py → Project1B0 / Project1B1
```

这条菜单流程**不会调用 `local_preexperiment.py`**。菜单中的“短测”是工程短测，不是已经完成的那种 200 步拟合加 5 轮预实验。

`server_train.py` 每次负责一个方向的一种方法；`server_launch.py` 负责依次安排多个实验。`ct-first` 是 CT 留出 G 的 B0 和 B1；`mr-first` 是 MRI 留出 E 的 B0 和 B1；`all` 是五个方向各两种方法，共十次训练。当前实现按顺序使用 GPU，不做多卡并行。

### 10.1 代码目录和输出目录是两回事

`CODE_ROOT` 指项目代码的位置。`ROOT` 是实际读写实验数据和结果的工作区：本机默认就是 project1；服务器由 `WHOLE_HEART_WORKSPACE` 环境变量指定，默认是 `project1/server_work`。

这就像“菜谱放在书架，做菜在厨房”：换服务器只需要重新定位数据和输出目录，不应到处手工改源码里的路径。

环境变量必须在导入相关模块之前设置，因为模块导入时就可能读取路径。`server_launch.py` 按这个顺序组织，初学者使用主入口即可。

### 10.2 为什么会有重复校验和工作区锁

路径和文件校验防止拿错数据；划分校验防止把测试病例混进训练；代码和环境哈希防止把设置不同的实验当成同一次续训；工作区锁防止两个进程同时写同一份结果。

这些检查会使程序在不确定时停止，而不是自动猜测标签或偷偷换数据划分。停止后的日志需要保留，用于定位原因。

## 12. 中断之后为什么需要检查点

检查点通常不只保存网络权重，还包括优化器、轮数和训练框架用于恢复的相关状态。只重新加载权重并不一定等于完整续训。

正式入口每轮保存，续训只选同一正式实验的 `checkpoint_final.pth` 或 `checkpoint_latest.pth`。不会拿工程短测权重替代，也不会把 `checkpoint_best.pth` 当成继续进度的首选，因为 best 可能来自更早的一轮。

`best` 表示按训练器内部开发指标保存的较好模型，不代表它一定是完整病例指标最优，更不是目标中心已经验证的最佳模型。最终评估采用什么选模规则仍须遵守研究方案。

恢复要求代码、依赖、划分和规划等匹配。中断恢复也不承诺抽样与随机增强逐位复现未中断时的过程，应保留中断事实。

## 13. 初学者建议按什么顺序读代码

不要从最长的训练循环开始。可以按下面五步读，每一步带着一个问题：

1. **数据是什么？** 先看标签表和 `data_pipeline.py` 的 `map_labels()`、`inverse_labels()`、`validate_geometry()`。目标是能解释图像、标签、空间矩阵的区别。
2. **哪些人参加训练？** 看 `splits_v1.json`，再看 `make_splits()` 和 `Project1B0.do_split()`。目标是能说明 ct_holdG 的 30/8/20 分别做什么。
3. **基线和增强差在哪？** 看 `Project1B0`、`Project1B1` 和 `appearance.py`。目标是能指出真正改变训练方法的几行。
4. **一次运行怎么组织？** 看 `server_launch.py` 的 `main()`，再看 `server_train.py` 的 `main()`。目标是区分任务调度与模型训练。
5. **结果怎么产生？** 先打开前期实验报告，再看 `local_preexperiment.py` 的 `predict()`、`dice_scores()`、`build_report()`。目标是把数字和保存它的代码对应起来。

看见下列 Python 写法时，可以这样理解：

| 写法 | 简单解释 |
|---|---|
| `import ...` | 使用另一个文件或软件包提供的功能 |
| `def ...` | 定义一个可以调用的功能 |
| `class ...` | 把一组相关状态与功能组织成一种对象 |
| `Path(...)` | 用统一方式处理文件路径 |
| `argparse` | 读取命令后面的参数，例如 `--check` |
| `if __name__ == '__main__':` | 直接运行这个文件时才执行下面的入口 |
| `assert` / `raise` | 发现不符合预期的条件时停止并说明错误 |
| `with torch.no_grad()` | 这段计算不建立反向传播所需的梯度记录 |
| `network.train()` / `network.eval()` | 切换网络训练/评估模式；本身不是开始一整次训练的命令 |

固定随机种子用于控制随机过程、核对初始化，但不表示 B0/B1 每一步抽到的块完全相同，也不保证不同硬件逐位一致。

运行不带 `--check` 的 `local_preexperiment.py` 会创建并训练一个新的 CT 预实验；服务器菜单选正式训练也会实际占用 GPU。二者不是查看结果的命令。

## 15. 什么可以改，什么需要当作新的实验

想了解某个病例属于哪组，先查清单，不必改代码。想更换服务器的数据目录，使用启动参数，不必改源码。想看分割效果，先读已有报告，不必重新训练。

如果修改排除病例、训练/验证划分、标签含义、网络规划、增强参数、训练轮数或初始化方式，就会影响实验解释，需要记录为方案或配置变化，不能无记录地接到旧实验上。

尤其不要直接把 421 改成 420，不要凭目标中心成绩反复挑增强参数，不要为了绕过错误删除划分校验，也不要把旧结果文件手工改成更好的数字。

`05_src` 中 Python 文件的哈希用于正式续训校验；即便只是修改注释，也会改变文件字节并可能触发续训保护。因此进行中的正式实验应保持代码版本稳定，学习笔记可以写在独立 Markdown 文档里。

## 16. GitHub 中保留什么，以及下一步还缺什么

GitHub 保存代码、环境配方、研究方案、病例划分清单、轻量日志、指标表和对比图。原始扫描、预处理缓存、三维预测影像、模型权重、环境本体不上传；未核实许可的作者参考脚本也按现有规则留在本地。

所以“从 GitHub 下载代码”不等于“同时下载到了训练好的模型和数据”。在另一台机器上运行，需要提供原始数据、搭建环境，并重新准备数据；若要继续本机模型，还需要另外传输匹配的检查点与实验状态，而不是直接选菜单就能找到它。

本项目下一阶段仍需完成：更充分的来源开发集检查、MRI 前期效果实验、完整 B0/B1 训练、外层目标中心的批量预测与统计、增强效果及失败病例分析。当前五轮 CT 的结果只支持继续观察学习过程，不能替代这些工作。

部分历史 README、状态 JSON 或方案文字记录的是当时的阶段，不会自动随每次训练更新。了解最近已经完成了什么，优先结合带日期的 [CT 前期训练报告](09_reports/20260920_CT前期训练结果.md) 和对应 `run.json`；了解原定实验原则，再读 [研究方案](01_protocol/研究方案_v0.1.md)。
