# 新版服务器面板：独立阶段与完整测评

对应面板v0.4.0。本机软件验证与服务器GPU验收分别记录；首次服务器运行先用完整测评采集现场证据。Skill暂不更新。

## 主菜单

| 入口 | 用户选择 | 自动处理 |
|---|---|---|
| 1 预处理 | 来源数据目录、预处理方法；当前只有nnU-Net默认方法时自动选定 | 独立输出、环境核验、数据与划分校验、来源fit规划、CPU/RAM/I/O约束、来源fit/cal预处理 |
| 2 训练 | 已完成的新版预处理任务、模型 | 校验并独立保存输入、CPU/GPU配置、实际尺寸容量测量、同一实验协同训练、检查点与日志 |
| 3 预测 | 已完成的新版训练任务及其模型 | 校验完整训练与冻结评价协议、空闲GPU逐病例推理、CPU原网格恢复及指标汇总 |
| a 完整测评 | 数据目录、模型、可选预处理方法 | 少量真实来源病例上的独立短流程，详细资源/优化/恢复/预测报告 |
| r 重启 | 新版任务 | 未完成任务从完整提交继续；已完成任务新建同阶段独立运行 |
| d 删除 | 新版任务并核对目录 | 阻止活动任务和有下游依赖的来源；移入同阶段可恢复回收区，暂不释放磁盘空间 |

保留任务概览、持续进度、显卡、模型、详细日志、进程、任务列表、结果、中断、程序更新、GitHub网络、代码上传及日志/指标/权重上传功能。旧的“新建后多选步骤”、单独续跑/独立重跑入口不作为新版日常菜单。

只读取`runtime/pipeline_v2/index.json`登记的新任务，不读取旧history/last-job或扫描旧结果目录。旧目录保留，环境、缓存、代理、SSH与更新配置仍使用原runtime。结果位于`结果根目录/pipeline_v2/prepare|train|predict|assessment/唯一任务`。

## 自动资源与训练预算

正式CT预算保持250轮、每轮250训练更新和50验证更新；学习率日程与来源/目标划分不静默改变。用户已允许自动调batch；预览、配置和日志明确记录原/实际全局batch、每卡batch、卡数及每轮patch采样量，不能把不同采样量称为同预算加速。

CPU根据当前亲和性、配额、空闲、RAM、共享内存与I/O生成有界候选；异步训练/验证池合并计入所有rank预算，worker使用1线程。源病例缓存惰性打开，不将已打开的全病例缓存复制进每个spawn载荷。能读取Linux PCI/NUMA映射时按GPU本地节点分配CPU分区，否则记录缺失并保留原分配范围。

GPU以实际卡数、当前可见/调度分配和连续空闲采样的交集为范围，约每1秒探测；无固定3/5卡上限。程序轻量CUDA保留和每卡锁用于协调本程序任务，不构成管理员级独占。只忽略本任务登记、PID身份匹配且owner仍存活的保留进程，其他计算进程即使0%利用率也不使用。

首次最多比较两个真实尺寸候选：2步预热、10步测量、2次验证、检查点保存/加载及恢复后更新。比较固定更新预算的预估轮次耗时，近似耗时下比较实测samples/s，同时记录采样变化、CPU资源和显存峰值。保留成功配置并记录失败候选；候选结果不能被称为全局最优或收敛证明。

同一实验使用每GPU一个DDP rank。后来空闲卡先保留，在完整轮次检查点处退出旧rank组，通过实际容量/通信/恢复测量后才重组加入并继续下一轮。检查点在同一原子文件内保存权重、优化器、scaler、轮数、日志、逐rank RNG和确定性取批状态。已有GPU按UUID恢复随机流，新GPU在明确记录的完整轮次边界使用确定性新流；更大batch/成员变化不宣称逐位相同轨迹。

选定训练和预测GPU阶段之间保留有效卡；全部GPU病例退出后、CPU收尾前释放保留卡。失败或任务退出也清理本任务子进程。没有结束的进程保留身份记录和继承锁，不据此声称清理成功。

## 测评范围与日志

默认Wholeheart来源fit8/cal4保持冻结。测评规划使用完整8fit以保持正式计划语义，实际只预处理/训练2fit、验证/预测1cal；不用selector、unlabeled或target调资源。完整来源导出与原始清单校验仍会读取必要的来源文件，不能把整个测评说成只访问3个文件。

每个候选12次训练加1次恢复更新；最多两个候选，不额外串行叠加完整smoke再训练一遍。第二候选可从第一候选短测检查点进入，验证卡组改变的恢复路径。测评权重与正式任务隔离，正式任务从seed0初始化；测评预测指标仅检查工程通路，不代表训练充分或分割效果。

主要证据位于任务工作区：

- `09_reports/assessment.json`：完整测评范围、阶段、选择、预测、验收边界。
- `diagnostics/resource-snapshot.json`、`missing-evidence.json`：实际采集、缺失项及其影响。
- `diagnostics/events/*.jsonl`：配置决定、候选失败、GPU采样（约5秒）与CPU/RAM采样（约30秒）。
- `07_experiments/tuning/*`：有界候选、rank输出、实际尺寸/显存/计时与检查点。
- `07_experiments/formal/*/training.log`、`progress.rank0.json`、`training_timing.rank*.jsonl`：轮次/loss、当前训练或验证批次、取批等待和步骤耗时。
- `07_experiments/**/ranks/*/rank-*`：每个进程独立stdout/stderr、结果与异常traceback。
- 任务根目录`launcher.log`、`logs/*`及`diagnostics/failure.json`：安装、阶段与失败现场。

只有整个测评包括预测/指标/资源释放通过，才向原runtime提交7天有效的优化建议。正式使用前核对数据、模型、计划、源标签、代码、环境、硬件、报告摘要和当前资源；失配或缺失则记录原因并重新做必要容量/调优检查。旧运行任务仍使用各自冻结源码，不热改。

## 已验证与待验证

本机Windows控制回归203项：195通过、8条件跳过；其中新版目录实际文件/失败注入31项28通过3权限跳过，实际junction和hardlink拒绝通过。实际nnU-Net2.8.1 CPU数据加载/增强串行与spawn及恢复一致；实际项目与固定版本检查点方法在CPU Gloo下验证2→3进程、旧UUID重排与新UUID加入、权重/优化器/RNG及下一轮取批和恢复更新。该测试使用微型Linear网络并绕过CUDA构造器，不代表完整nnU-Net训练。实际NibabelIO非立方体预测的坐标、体素、仿射和标签写出/指标通过。另用60例合成影像跑通清单、划分、完整8fit规划和3例测评预处理，48份禁止读取的原始标签故意无效且保持不变。使用的本地Torch为2.12.1，目标仍是2.8.0+cu128，CPU证明不替代目标CUDA/NCCL验收。结构化记录见SERVER_PANEL_V2_VALIDATION.json。

一次额外的完整CPU构造器探针在本机Windows的gamma数据增强中发生原生访问异常，未计为通过；其源代码和故障日志独立保留，没有修改正式增强方法或库。受管进程已启用Python原生故障栈日志。此探针与目标Linux/Torch2.8 CUDA栈不同，目标实测仍必需。

服务器登录认证当前不可用，未运行远程训练。服务器8×3090等记录来自历史及用户报告；本机4060 Laptop不是服务器性能证明。本机只读GPU检查发现已有计算进程，因此没有启动GPU测试。实际Linux锁继承、NCCL、完整尺寸峰值与吞吐、真实数据全流程由服务器完整测评产出，未通过前不称为已验收。
