# 环境检查与依赖修复（面板0.5.1）

## 入口与顺序

主菜单 `e 独立环境准备/检查` 可单独安装或核验环境，无需数据或GPU。
每次预处理、训练、预测、完整测评也会先执行：独立环境安装/修复 →
实际依赖导入与进程资源API检查 → CPU前向/反向和检查点小测 → 计算阶段。
安装细节看该任务 `launcher.log`，安装阶段状态见 `environment.json`，CPU小测见
`software-smoke.json`。各阶段日志不等于安装总日志。

0.5.0新增的资源观测使用psutil，但安装声明和前置检查遗漏了该依赖；
因此可能在病例计算后记录RSS时才失败。0.5.1把psutil列入Conda规格，
`runtime_setup.verify_dependencies`统一检查固定版本、实际运行依赖导入及
`task_resources.process_observation`。即使ready指纹一致也重新实际检查，失败则进入
本项目独立环境修复；修复后检查仍失败时，不进入数据计算，不声称安装完成。
`pip check`只能检查包声明的依赖关系，不能代替项目自己的导入和实际API检查。

## 更新后的处理

保持原runtime，更新并重新打开面板，核对版本0.5.1。
输入e，选择1，按现有RUN确认提交环境准备，待其完成后查看总日志。
此前因缺依赖失败的旧预处理任务保留原样，改用1创建新的预处理任务。
旧任务冻结源码及pip/Conda环境记录；补装依赖后直接重启，可能因记录不符被拒绝。
不要删除或覆盖旧环境记录、伪造缓存签名，或把任务标成已完成。
本修复未改变七文件预处理身份及科学流程，但来源任务还保存完整依赖清单；
只有实现和依赖记录均兼容时旧准备才可继续使用。若安装更新改变了依赖清单，
新训练也会拒绝该旧来源，需在新环境新建预处理；不要覆盖来源环境记录绕过校验。

## 安装源与代理边界

已有Conda优先复用；缺少时从官方GitHub下载并校验Miniforge。
基础依赖来自conda-forge（nodefaults），PyTorch/torchvision来自官方cu128索引，
nnU-Net/threadpoolctl来自pypi.org。无默认国内镜像。
用户要求安装直连优先：Conda/pip/Miniforge每个下载操作先用不带代理的子进程/显式空代理opener，
失败后读取原runtime的c网络配置，使用其代理重试一次；无配置或第二次失败则停止。
直连成功不尝试代理；用户中断不触发重试。若首次创建留下部分环境，代理阶段改用同规格env update，
保留文件，不删除重建。Conda仅使用一次性的线路配置，并核对实际生效的proxy_servers；
外部强制配置覆盖本次线路时明确停止，不能假称直连。HTTP连接/读取超时和重试均有界，
不把包管理器内部重试当作额外线路。每次线路/尝试次数和失败信息写入安装总日志及environment.json。
面板c仍用于GitHub更新/上传，本补丁未改其已验证的代码下载机制。
不修改全局Conda/pip、系统代理、TLS验证或其他训练环境。

## 验证边界

回归覆盖缺psutil、原生库导入失败、资源API实际调用、CPU小测失败落盘，以及
Linux安装控制中的同指纹缺包修复和导入失败禁止ready；Linux专属测试在Windows明确跳过。
真实服务器Conda下载、安装、病例预处理仍需在目标环境确认，不把本地模拟当作服务器验收。
