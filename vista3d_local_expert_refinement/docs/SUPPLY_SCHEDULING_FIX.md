# 0.7.2 供数调度修复

本次只修复 CPU 病例队列重复扣减预算和传输双缓冲等待未来批次；不改变数据协议、预处理数值、采样、模型、loss、固定 global batch、优化器、扩卡判据或编译策略。

## CPU 病例准入

`cpu_case_queue.run` 在阶段开始保存 CPU、RAM 和 worker 上限。后续准入同时检查阶段总额度及实时新增余量，不再从实时剩余 CPU 中扣一次已分配线程，也不把按剩余资源计算的 worker 数当成包含已运行任务的总上限。

RAM 总预留仍受阶段上限约束；实时余量只再扣已运行病例尚未兑现的预留。兑现量只采用仍由本队列持有、存活且出生身份未改变的直接子进程 USS；无 USS、进程退出或身份改变时兑现量为零。共享 RSS 和未核实的后代内存不用于抵扣。实时外部占用仍会阻止新增任务，资源从已知变未知时回到有界串行准入。预算与估算不构成硬内存限额。

受控回归中，16 CPU 的 80% 阶段预算可启动 12 个单线程任务；RAM=100、每例=10 的 80% 阶段预算可启动 8 例。另测未兑现预留、外部抢占、未知资源、进程退出和 PID 复用；这些是准入控制结果，不是实机吞吐倍数。

## 就绪批次与双缓冲

`EpochBatchIterator.ready()` 只非阻塞接收已返回的 worker 消息，且要求下一消费序号已经就绪；后序号先返回或仅完成 SHM 请求握手不会误报可取。生成及 RNG 作用域仍在原调用路径。

`BatchTransfer` 的首批按需获取；已有一批排队时，只在来源明确 ready 后读取下一批。串行或无 ready 接口的来源按需读取，不为填满两槽阻塞当前批次。worker 已完成时仍可使用两槽、原 CUDA event/storage 复用与未消费批次重放；不宣称每一步必定实现拷贝/计算重叠。

## 旧任务与输入

`prediction_code_compatibility.json` 追加完整代码映射的精确 0.7.1→0.7.2 边，保留 0.7.0→0.7.1，已完成旧训练可用于新预测。`preparation_code_compatibility.json` 新增七个生产者文件映射的精确兼容边，菜单、提交和实际准备检查共同使用；数据、计划、环境及其余签名字段仍严格比较。

复制旧输入不修改源任务；需升级当前工作副本的准备签名时，先按原签名摘要保留独立备份。未知代码、缺失审计及其他身份差异仍拒绝。旧未完成任务继续用冻结源码恢复，不热修，也不改旧记录以绕过校验。
