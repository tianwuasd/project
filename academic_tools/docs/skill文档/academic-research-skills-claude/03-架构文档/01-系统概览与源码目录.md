# 系统概览与源码目录

> 版本说明（2026-10-19）：源码已更新；正文保留此前整理的指南，功能与安装入口以当前上游 README 为准。见[本次更新记录](../../../../UPDATE-2026-10-19.md)。

## 1. 项目技术形态

Academic Research Skills（ARS）Claude Code 版是一个**多 Skill 研究工作流插件**。它的核心不是传统应用服务器，而是一组由 Claude Code 发现和解释的 Markdown 工作流，以及用于确定性校验的 Python/Shell 脚本。

项目可以分成五层：

```text
┌─────────────────────────────────────────────┐
│ 宿主层：Claude Code / Plugin / Project Skill │
├─────────────────────────────────────────────┤
│ 入口层：4 Skills + 16 Commands + 3 Agents    │
├─────────────────────────────────────────────┤
│ 编排层：Pipeline / State / Checkpoints       │
├─────────────────────────────────────────────┤
│ 能力层：Research / Paper / Reviewer          │
├─────────────────────────────────────────────┤
│ 基础设施：Shared Contracts / Scripts / Hooks │
└─────────────────────────────────────────────┘
```

### 为什么这样拆分

- 用户只需要文献研究时，不应加载完整论文生产流程；
- 写作、审稿和研究的输入输出不同，需要独立契约；
- Pipeline 只负责协调，避免编排器同时承担所有专业工作；
- 需要精确、可重放的检查交给脚本，生成性判断保留在 Agent prompt；
- `shared/` 统一跨阶段 Schema，防止各 Skill 对同一字段产生不同理解。

## 2. 四个顶层 Skill

| Skill | 源码入口 | 主要职责 | 何时使用 |
|---|---|---|---|
| Deep Research | `deep-research/SKILL.md` | 研究问题、检索、来源核验、综合、系统综述、事实核查 | 任务重心是“找到和理解证据” |
| Academic Paper | `academic-paper/SKILL.md` | 配置、结构、论证、起草、引用、修订、格式化 | 已有问题或材料，重心是“形成论文” |
| Academic Paper Reviewer | `academic-paper-reviewer/SKILL.md` | 多视角审稿、编辑决定、修改路线和复审 | 已有稿件，需要独立评估 |
| Academic Pipeline | `academic-pipeline/SKILL.md` | 检测当前阶段、调度前三个 Skill、维护状态、门禁和交接 | 任务横跨研究、写作、审稿和修订 |

### Pipeline 不是什么

`academic-pipeline` 源码明确把自己定义为 lightweight orchestrator。它不会替代：

- `deep-research` 的检索和综合；
- `academic-paper` 的论证与起草；
- `academic-paper-reviewer` 的独立审稿；
- 研究者对方法、数据、引用和最终结论的判断。

因此，单一任务应直接选择下游 Skill，不必为了“完整”而启动 pipeline。

## 4. 核心板块职责表

| 板块 | 它解决什么问题 | 什么时候参与 | 新手需要直接阅读吗 | 是否直接修改 |
|---|---|---|---|---|
| `.claude/CLAUDE.md` | 解决跨 Skill 意图冲突和路由纪律 | Claude Code 在仓库上下文中工作时 | 想理解路由时建议读 | 维护者修改，需同步路由语义 |
| `.claude-plugin/` | 告诉 Claude Code 这是哪个插件、暴露哪些 Skill | 插件安装和发现时 | 一般不需要 | 版本/分发变化时修改 |
| `skills/` | 提供宿主要求的发现形状 | 项目级或插件级发现时 | 排查“找不到 Skill”时读 | 不作为业务真源修改 |
| 四个 `SKILL.md` | 定义触发、mode、阶段、边界和产物 | 每次进入对应 Skill | **首先阅读** | 是，各 Skill 的主协议 |
| `agents/`（各 Skill 内） | 把大任务拆成职责明确的角色 | 工作流进入相应 phase 时 | 遇到具体阶段再读 | 是，遵守阶段边界 |
| 根 `agents/` | 暴露三个插件 Agent | 插件注册 Agent 时 | 通常不需要 | **不能作为真源手改** |
| `commands/` | 将短命令映射到 Skill + mode | 使用 `/ars-*` 时 | 想看命令映射可读 | 修改 mode 时同步 |
| `hooks/` | 会话公告和写入前辅助保护 | SessionStart、Write/Edit/Bash 前 | 直接读源码时可忽略 | 可修改，但不能替代核心 gate |
| `shared/` | 统一跨阶段字段、状态和交接语义 | Skill handoff、Passport、审查契约时 | 理解数据结构时重点读 | 跨 Skill 变更的主要位置 |
| `scripts/` | 将部分检查变成确定性、可重放程序 | 引用、schema、patch、CI、审计时 | 普通使用按需 | 是，需配测试和 fixtures |
| `docs/` | 解释架构、能力、安装、数据流和风险 | 学习、排错、维护时 | 建议按主题读 | 可修改；生成文档除外 |
| `evals/` | 校准和评估 Agent/流程表现 | 开发、回归和 bakeoff 时 | 普通使用不需要 | 谨慎；gold 不得泄漏给候选生成 |
| `audits/` | 记录真实审计结果和治理状态 | 发布、风险评估时 | 普通使用不需要 | 作为审计记录维护 |
| `tools/release-discipline/` | 保证命令、公告、版本和 CHANGELOG 一致 | 发布前 | 不需要 | 发布维护者使用 |

## 5. Canonical、镜像与生成物

### 5.1 四个 Skill 的 canonical 源码

以下目录是行为真源：

```text
deep-research/
academic-paper/
academic-paper-reviewer/
academic-pipeline/
```

它们根部的 `SKILL.md` 定义顶层入口。`skills/` 是发现层，不应当被理解为另一套业务实现。

### 5.2 插件公开 Agent 镜像

根 `agents/` 中：

- `synthesis_agent.md`
- `research_architect_agent.md`
- `report_compiler_agent.md`

应与 `deep-research/agents/` 中同名源文件保持字节一致。修改流程：

```text
修改 deep-research/agents/<agent>.md
→ 同步到根 agents/
→ 由 scripts/check_agents_mirror_sync.py 检查
```

不要只修改根镜像，否则下次同步会覆盖或造成两个入口行为不同。

### 5.3 生成文档

`docs/STAGE_CAPABILITY_MATRIX.md` 是生成结果，真源是：

```text
shared/contracts/capability/stage_capability_matrix.json
```

变更能力矩阵时应修改 JSON 真源，再使用仓库 renderer 生成 Markdown；不能只改生成页。

## 6. 四个 Skill 内部的共同结构

典型 Skill 由以下元素组成：

```text
SKILL.md
├── frontmatter：名称、描述、版本、状态和相关 Skill
├── trigger / non-trigger：什么时候进入或避开
├── modes：同一能力的不同深度或目标
├── phases：阶段顺序
├── agents：每个阶段的角色
├── references：细化协议和判断规则
├── templates：产物结构
└── handoff：交给下游的字段和状态
```

不是每个引用都在启动时读取。合理顺序是：先读 `SKILL.md`，确定 mode 和当前 phase，再加载该 phase 所需 Agent、reference 和 template。
