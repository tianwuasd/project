# 学术工作 Agent 建设计划

> 执行说明：这是待用户讨论的分阶段建设计划，本轮不执行实现。开始建设时使用 `superpowers:executing-plans` 按任务推进；每阶段达到验收条件后再进入下一阶段。具体接口实现随 M0 的环境验证结果细化。

**Goal:** 建立从多源文献发现到有证据的研究分析与写作的可扩展个人研究系统。

**Architecture:** Python 研究内核维护文献、证据、版本和任务；LangGraph 负责阶段控制；Codex/API 通过统一后端契约运行受限模型任务。第一版先交付可恢复的“检索—精读—综述”闭环。

**Tech Stack:** Python 3.12（M0 验证后锁定）、SQLite、本地文件、LangGraph、Codex Python SDK 或独立 API 适配器、可替换 PDF 解析器。MVP 不要求独立网页、GPU 或云服务。

**Spec:** [架构方案](D:/code_project/academic_tools/docs/superpowers/specs/2026-09-07-academic-agent-design.md)。

## 全局约束

- Windows 本地个人项目优先；新代码建议放在 `D:\code_project\academic_agent`，当前文件仅规划，不创建该代码工程。
- 原文、文献和主张的权威状态在本地；索引和会话历史可重建。
- `metadata_only` / `abstract_only` / 全文状态必须明确，不虚构读取范围和实验结果。
- 单一提交者写权威数据；领域产物先原子提交，后更新流程检查点。
- 文件先完成不可变落盘及哈希核对；登记时拒绝过期尝试、取消任务和旧输入的迟到结果。
- 模型后端和数据源可替换，不能自动继承当前桌面工具、登录或插件。
- 默认不超过 100 条去重候选、10–20 篇全文、3 个并发模型任务。
- 试点最多 2 次网络重试、每节点最多 1 次输出修复、每分析最多 2 轮定向补检索、审查修订最多 2 个往返。
- 所有经验性主张都关联可定位证据；身份核验、摘录匹配与语义支持分别检查。
- 文献更新或人工修改导致下游依赖失效；未解决的缺口保留在成果中。
- 首次入库与 MVP 导出前检查出版状态；计量快照冻结纳排决定、版本和去重关系，计数单位默认是去重文献组。
- 不把文档阅读、mock 测试或单条接口成功当作系统性能验证。

## 里程碑与交付

| 阶段 | 可独立验收的交付 | 完成标志 | 相对投入 |
|---|---|---|---|
| M0：可行性与契约 | 环境报告、固定样本、后端/来源能力表、契约定义 | 本机能安全运行最小后端任务，退出及恢复路径明确 | 小 |
| M1：可信文献库 | 多源检索、规范化、版本去重、筛选清单、导入导出 | 固定测试集上检索可回放，故障不会变成零结果 | 中 |
| M2：精读到综述 | 证据卡、比较矩阵、引用综述、独立审查 | 文献与语义两类验收达标，能中断恢复 | 较大；至此是 MVP |
| M3：趋势与创新 | 冻结语料分析、创新候选与反证、验证方案 | 统计可复算，结论强度与证据一致 | 中至较大 |
| M4：写作与特化 | 写作修订、领域包、专题增量、按需 UI | 人工修改不丢失，扩展无需改核心，更新有影响追踪 | 按题目决定 |

日历工期和费用在 M0 后估算：当前没有具体题目、语料规模、API 预算和 PDF 难度，不能给出可信的固定报价。每阶段单独评审投入与结果，MVP 未达标前不扩张到完整平台。

projects/          # 各研究项目的私有数据；不提交原文或密钥

## Task 0：环境与最小后端契约（M0）

**计划文件：** `contracts/job.py`、`contracts/project.py`、`backends/base.py`、`backends/codex.py`、`backends/replay.py`、`tests/backends/test_contract.py`、`docs/readiness.md`。

**接口设计：** `Backend.run(job: ModelJob) -> ModelResult`。输入包括任务 ID、指令版本、输入产物引用、结果 schema、允许工具、文本/图像能力要求、超时和预算。输出包括状态、结构化内容、实际模型、用量（未知可为空）、错误类型和可恢复标识。`Backend.capabilities()` 声明支持的能力，调度前检查。

- [ ] 检查独立 Python 环境、SDK 可执行文件、SQLite 和 PDF 依赖兼容性，写出锁定版本；不修改现有参考仓库。
- [ ] 使用离线回放后端证明结构化结果、失败、超时和用量未知都可以被同一契约表达。
- [ ] 在正式实现前按用户选择配置 Codex 登录或 API 凭据；只验证存在和可用性，不输出凭据。
- [ ] 用一份人工准备的非敏感短材料运行真实后端，验证结构化输出和受控工具权限。
- [ ] 在能力表记录权限限制的执行位置，并用构造的任务外文件/禁用工具及论文内指令做负向验证；提示词约束不能充当沙箱证明。
- [ ] 测试取消、结构错误和重启；记录 SDK 会话恢复与项目恢复的区别。
- [ ] 保存每个来源的可用性和限额探测结果，确认单条成功不代表批量配额。

**验收场景：** 后端要求图像但不支持时，在发起请求前返回 `unsupported_capability`；超时保留工作 ID，不能伪装成成功；结果没有用量时显示“未知”。M0 未确认可用的后端不参与后续模型验收。

## Task 1：搜索、规范化与文献版本（M1）

**计划文件：** `contracts/search.py`、`contracts/work.py`、`sources/base.py`、`sources/openalex.py`、`sources/semantic_scholar.py`、`sources/crossref.py`、`sources/arxiv.py`、`sources/imports.py`、`storage/work_repository.py`、`tests/sources/test_search_contract.py`、`tests/test_dedup.py`。

**接口设计：** `Source.search(query: SourceQuery, cursor: str | None) -> SearchPage`。返回记录、下一页、原响应引用、截断标记和 `ok/empty/partial/unavailable/rate_limited` 状态。`resolve(identity: WorkIdentity) -> Resolution` 返回字段级证据及冲突，不返回虚构书目信息。内核负责把 `SearchPage` 规范化为 `Work` 和候选版本关系。

- [ ] 建立中英文查询计划、来源专用查询转换及原始响应保存；查询词转换必须可回看。
- [ ] 首先实现 OpenAlex 和 Semantic Scholar 两个发现适配器；Crossref 负责书目补充与 DOI 核对；arXiv 单独启用或降级。
- [ ] 实现每来源限速、分页、截断、超时、失败隔离和预算占用。
- [ ] 实现 ID 优先匹配和保守的模糊去重；疑似相同文章可人工合并/拆分。
- [ ] 首次入库检查撤稿/更正及版本状态，记录来源、时间、未知和过期状态，不把无信息当作正常。
- [ ] 支持本地 PDF 元数据输入及 RIS/BibTeX 导入导出，保留无 DOI 文献。
- [ ] 保存筛选理由，并对排除结果做分层抽查；资料不足进入待判定。

**验收场景：** DOI 大小写/URL 前缀变体归一；同题不同作者不误合并；同一 arXiv 不同版本相连但不覆盖；会议版与期刊版有关系而非默认同一证据；中文无 DOI 文献不被判为伪造；首次导入即已撤稿的论文被标出；第二页失败产生部分结果；接口故障不被记录为零命中。真实联网测试只用小样本，回归测试用冻结响应。

## Task 2：解析、证据和精读卡（M2 前半）

**计划文件：** `contracts/document.py`、`contracts/evidence.py`、`contracts/claim.py`、`acquisition/fulltext.py`、`parsing/base.py`、`parsing/docling.py`、`evidence/register.py`、`evidence/verify.py`、`capabilities/reading.py`、`tests/evidence/test_grounding.py`。

**接口设计：** `Parser.parse(document: DocumentVersion) -> ParsedDocument`；`Reader.extract(question, parsed_document) -> ReadingCard`；`Verifier.check(claim: Claim, document_version, spans, read_context) -> VerificationReport`。提取器只能引用真实 `EvidenceSpan` ID；`read_context` 是按确定文档版本取得章节或检索结果的只读工具。核验器分别返回身份、定位、摘录匹配、语义支持、数值一致性及实际检查范围。

- [ ] 建立全文状态及哈希版本；确认下载内容是目标论文而非登录页或错误页。
- [ ] 实现文本层解析，复杂 PDF 由可替换版式/OCR 解析器处理；保存定位和解析诊断。
- [ ] 按小节提取阅读卡，区分作者主张、结果、假设和未报告内容。
- [ ] 将结果数值绑定原表/段落及研究条件；难以定位或识别时输出待核项。
- [ ] 设计片段检索与上下文补充，避免只根据一句摘录忽略否定词或限制条件。
- [ ] 允许审查者独立读取方法/结果/局限章节，而不受生成者选出的摘录集合限制；所需上下文不可用时保持证据不足。
- [ ] 用独立评审上下文核查原子主张，而不是仅审查生成摘要。

**验收场景：** 摘要输入不得输出全文独有的消融结果；不存在的 evidence ID 必须被拒绝；摘录精确匹配但曲解结论仍判失败；改变一个数值或否定词能被发现；扫描件定位失败保持未核；同一文献新版不会静默替换旧版证据。

## Task 3：可恢复的综述闭环（M2 后半，MVP）

**计划文件：** `workflow/review_graph.py`、`workflow/budget.py`、`storage/committer.py`、`storage/dependencies.py`、`capabilities/comparison.py`、`capabilities/writing.py`、`capabilities/review.py`、`exports/markdown.py`、`exports/bibtex.py`、`tests/workflow/test_resume.py`、`evals/run_mvp.py`。

**接口设计：** 各阶段消费已经提交的产物 ID 并产出候选 `AnalysisArtifact`；`Committer.commit(job_id, attempt_id, lease_token, expected_project_revision, input_hash, artifacts)` 核验文件及任务仍有效后，原子登记产物及依赖。`Writer.draft(outline, claims) -> DraftVersion`；`Reviewer.review(draft, evidence, document_versions, read_context) -> ReviewReport`。检查点仅引用已提交的 ID。

- [ ] 串联研究项目、检索、筛选、阅读、比较、大纲、写作和审查。
- [ ] 独立论文最多 3 个模型任务并行，由单一提交者写数据库。
- [ ] 添加输入/版本/配置幂等键，测试“提交后、检查点前”崩溃恢复。
- [ ] 实现不可变产物落盘、有效尝试与项目修订号比较；测试文件写完数据库未提交、取消后迟到提交、旧输入迟到提交。
- [ ] 加入预算预留、重试上限及停止报告；保留超时后费用未知的状态。
- [ ] 预算实现已预留/确认消耗/确认未消耗/待对账，待对账继续占用且重试另预留；用量不透明后端按任务数、耗时和并发限制。
- [ ] 导出前检查引用文献的出版状态，处理已知撤稿/更正及其依赖影响；来源不可用则披露未知或过期信息。
- [ ] 从稳定引用键导出综述、文献库、比较表、证据表、检查报告和未解决问题。
- [ ] 在固定保留集上评测，并与单 agent 直接读同一材料的简单基线比较。

**验收场景：** 阅读第 6 篇时退出，恢复后前 5 篇产物复用；并发重试不重复登记引用；错误分支仍保留成功来源；人工剔除论文后相关段落失效；预算不足时不发起新任务；核心主张证据不足则删除、弱化或标明缺口。

## Task 4：趋势、研究空白与创新候选（M3）

**计划文件：** `capabilities/corpus.py`、`capabilities/trends.py`、`capabilities/novelty.py`、`capabilities/countersearch.py`、`tests/analysis/test_corpus_counts.py`、`evals/novelty_cases.jsonl`。

**接口设计：** `CorpusSnapshot` 固定文章集合、文档版本、检索、纳排决定、去重/家族关系、日期口径及标签版本；`ComputationRecord` 记录输入快照、代码/公式及版本、参数、结果表与哈希。`TrendReport` 关联该计算记录并返回图表和覆盖限制；`NoveltyCandidate` 返回最邻近工作、差异、反证、假设和最低验证方案。

- [ ] 区分发现候选集和计量分析语料，提供冻结快照与可复算统计。
- [ ] 先交付年度计数、方法标签和语料内占比；当前未完成年份独立显示。
- [ ] 默认用去重文献组计数，不把它称为统计独立研究数；疑似重复单列合并/不合并的敏感性结果，关系变化生成新快照。
- [ ] 进行查询词、日期口径、预印本去重的敏感性检查，再决定是否加入聚类和引文图。
- [ ] 分开提取作者贡献与系统提出的研究候选；每个候选检索最接近的已有工作及反例。
- [ ] 为候选给出最低可证伪的实验/实证设计，列出必需数据和已知障碍。

**验收场景：** 已确认属于同组的预印本和正式版不增加去重文献组计数；只有 top-k 数据时不能输出领域增长率；去重关系修订生成新快照，旧图表仍能复算；已知相同方法的论文被加入后，候选不能仍声称未见先例；只有 3 篇文章时可以比较，但不生成有把握的全领域趋势结论。

## Task 5：论文写作、领域插件和专题更新（M4）

**计划文件：** `contracts/plugin.py`、`capabilities/revision.py`、`capabilities/updates.py`、`profiles/general.yaml`、选定领域包、`interfaces/cli.py`、按需 `interfaces/mcp.py`、`tests/test_plugin_contract.py`、`tests/test_revision_invalidation.py`。

- [ ] 用真实课题确定领域字段、数据库和评价准则，建立一套小型领域保留集。
- [ ] 在不修改核心的条件下加载领域包，并用相同输入比较通用版与领域版的结果。
- [ ] 接入用户真实实验产物，保存来源与版本，支持章节写作和审稿回复草稿。
- [ ] 保留人工修改，针对新增/改变的主张重跑核验，提供修订差异。
- [ ] 增量文献及撤稿/更正更新触发依赖失效和影响清单。
- [ ] 根据实际使用频率决定是否建设网页或直接连接 Zotero；定时追踪由用户选择时间后再配置。

**验收场景：** 领域包只增加必要字段及规则；禁用插件后通用流程仍可运行；用户改动结果数值会触发重核；更正论文被识别后相关正文明确标记；新一次运行不覆盖人工正文。

## 多轮质量验收

以下均为未来产品验收设计，本轮没有执行这些评测。

1. **确定性检查：** 数据契约、ID/版本、引用键、原文位置、数值、预算、去重和恢复。
2. **独立证据审查：** 审查者从原文出发检查支持关系、反例、研究条件和漏掉的限制。
3. **保留集验收：** 固定题目、论文、人工标签，报告检索与写作的分项表现及失败样例。
4. **真实课题试用：** 用户评估“是否减少检索和核查负担、能否继续写作”，据此决定下一阶段。

评测准备建议：M0 仅准备短材料和最小故障样例，完整标注在 M2 验收前完成。使用 3 个小主题（通用方法、理工方向、经济/社会科学方向），每题 10 篇人工确认种子论文；按主题各划分开发与保留种子，保留集合不用于调参。另建 60 对重复/非重复书目记录、12 篇不同版式和读取状态的文档、至少 120 条人工标注原子主张；每篇适合精读的全文文档再标注 3–5 个必须覆盖的重要发现/局限，综述任务标注必须覆盖的关键分歧。主题只是能力测试，不代表用户最终选题。

检索标签由人工核对不同来源和种子引文链建立；仍只代表相对于已知相关集合的召回率。精读与写作标签由阅读原文的人建立，分歧经过裁决；模型可以辅助标注，但不能自己生成并给自己判满分。

| 指标 | 试点验收目标 | 解释与防止误用 |
|---|---|---|
| 文献与来源可追溯 | 导出文献记录 100% 有来源 ID 或可定位的人工导入记录 | 无 DOI 不算失败；虚构 DOI 算失败 |
| 引用完整性 | 导出引用键 100% 可解析，悬空引用为 0 | 这是结构指标，不代表语义正确 |
| 种子检索召回 | 已知保留种子总体 ≥80%，逐主题报告 | 小样本且非全球召回证明；不能隐藏某主题失败 |
| 前 20 条相关性 | 每主题 P@20 目标 ≥75% | 不足 20 条按实际分母并披露 |
| 去重 | 固定 60 对中不同研究误合并为 0，同篇漏合并 ≤1 对 | 同研究版本关系另外报告 |
| 主张支持 | 随机抽样的原子经验性主张 ≥95% 受到引用支持 | 同时报数量/分母/不确定性；关键主张逐条检查 |
| 关键信息覆盖 | 精读卡/真实综述的人工必覆盖信息 ≥90%；已给充分证据却错误拒答 ≤10% | 与支持率同时达标；空白、删光难点或只写容易支持的句子不能通过 |
| 摘要越权与虚构 | 人工构造的缺全文、伪 DOI、改数值、否定词用例全部识别 | 通过这些用例仍不代表所有场景无幻觉 |
| 创新表述 | 每张候选卡包含近邻、反例检索和最低验证方案；无证据全球首次断言为 0 | 评价可研究性，不以模型自评分作为创新证明 |
| 崩溃/并发/预算 | 每个指定失败注入点均能正确停止或恢复，无重复权威记录 | 外部调用费用未知需明确列出 |
| 多 agent 的增益 | 对同一语料比较关键错误数、用量和耗时 | 没有可见质量收益的角色合并或取消 |

这些数值是拟议试点门槛，不是已实现成绩。关键证据错误未解决时不发布“已核验”结论；小样本结果不外推为普遍质量承诺。

## 每次运行应留下的成果包

建议结构：项目说明、检索方案和来源日志、去重文献库、筛选清单、论文精读卡、比较矩阵、正文草稿、参考文献、主张—证据对照、质量报告、失败与缺口、运行成本和恢复记录。

M3 再增加趋势数据与图表、创新候选卡、验证方案；M4 增加人工修订记录、审稿回复草稿、更新影响清单。每个产物包含输入快照和版本，用户可以沿正文回到原始论文。
