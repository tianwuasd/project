# 中断后如何继续（0.7.0 起）

先确认原任务已经退出。`stale` 仅说明原主进程已退出或启动身份不符；子进程可能仍在运行，应检查并通过 `--stop` 停止；日志停在某病例只表示该病例开始处理，不表示它完成。日志没有 OOM 信息、但无权查看系统日志时，不能排除或认定 OOM。

```bash
bash start_server.sh --status
# 需要主动停止正在运行的任务：
bash start_server.sh --stop
# 等待状态显示停止后，恢复最近一次流程：
bash start_server.sh --resume-job
```

也可运行 `bash start_server.sh` 进入任务面板，0.9.0 起选 `r` 会列出历史任务，再选择需要续跑的编号；0.15.0 起已完成任务也能追加原计划中没有的步骤；成功步骤锁定复用，不会重复运行。运行中选 `x` 显示目标名称/目录并确认停止，选 `s` 查询退出状态。恢复保留原名称，不用 `--name` 重命名。GPU 步骤在选择前显示当前显卡状态，可重新选择获准且空闲的卡；纯 CPU 流程不询问 GPU。非交互恢复沿用原分配，也可显式覆盖 `--gpu` 和 `--gpu-count`。数据、模型设置、划分、步骤顺序和路径使用原 `plan.json`，不从最近新建任务的设置猜测。自定义 runtime 需要传相同的 `--runtime`。

恢复特定旧流程（将路径换成实际 workflow，不是步骤子目录）：

```bash
bash start_server.sh --resume-job /完整结果路径/某次_workflow
# 无人值守恢复；仅在确已获准使用 GPU 7 时指定：
bash start_server.sh --resume-job /完整结果路径/某次_workflow \
  --gpu-count 1 --gpu 7 --non-interactive
```

后台方式仍可断开 SSH。提交成功只是任务已提交，查看原 workflow 的 `launcher.log` 和 `--status`。不手动删除锁文件，不把多个后台命令用 `&&` 当作串行等待。

0.8.0 起，恢复时 `--gpu-count` 表示最多并发卡数，不要求一次凑齐。`waiting_gpu` 是等待资源而非中断；有一张符合原空闲门槛的候选卡即可继续，后续空闲卡加入剩余阶段。可以 `--stop` 停止等待，再用同一 `--resume-job` 恢复；数据、训练配置和已有检查点不因少卡调度而改变。

## 各步骤恢复边界

| 步骤 | 中断后的处理 | 最大重复工作 |
|---|---|---|
| 环境检查 | 重做未完成检查；依赖安装沿用已有环境 | 本次检查/未完成安装；不自动删除不完整 Conda 目录 |
| 预处理 | 校验原始影像、标签、参数及缓存哈希；完整病例保留，损坏或缺失病例重做 | 当前未完成病例 |
| 软件短测、正式尺寸预检、正式训练 | 每阶段 `.last.pt` 恢复模型、Adam、CPU/CUDA/NumPy/Python 随机状态；完成阶段无需再做梯度计算 | 当前未提交的 epoch；smoke/preflight 每阶段最多一组短测 |
| 独立预测 | 校验模型、缓存、病例范围以及 NIfTI/网格文件哈希；保留完成病例 | 当前未提交病例 |
| 测试集预测和评估 | 接续预测；评估重新汇总完整病例集 | 当前预测病例及一次评估汇总 |
| 独立分割评估、标签导入、诊断特征、诊断树、诊断与解释、诊断评估 | 中断步骤旧目录改名为 `.interrupted-<标识>`，该步骤从头重跑；其他已完成步骤经校验后保留 | 当前短步骤；没有宣称这些步骤支持病例/迭代级续跑 |
| 合成演示 | 保留旧输出后从头重跑 | 当前演示 |

正式训练恢复仍先做真实尺寸预检。更换 GPU 数量/编号只改变独立阶段的调度，不合并显存。不同 GPU、驱动或库版本之间不保证逐比特数值一致；本机 CPU 回归验证同环境中断与连续训练的权重、优化器和随机状态一致。

三折模式先校验根 `training-contract.json` 中的数据、配置、缓存哈希和患者名单，再逐折核验。已完成折完整保留；中断折从各阶段 `.last.pt` 接续。启动时冻结的配置供三折共用，运行期间修改源 YAML 不影响后续折；续训仍须提供与原任务一致的配置。折清单、权重或患者划分被更改会报错。阶段子进程同时继承根三折目录与当前折的锁，服务器停止/恢复会检查三个折目录中的进程记录。

## 旧版本的兼容范围

- **0.6.0 中断预处理**：没有逐病例旁车记录。首次恢复会重新读取原始数据并计算预期数组，与已有 `.npz` 比较；完整缓存不重新压缩、不改时间戳，缺失/截断缓存重新保存。原始读取和校验仍需要时间，不会直接跳到日志显示的第 85 例。后续使用 `.resume/` 记录按哈希校验，不再重做已完成病例的归一化。
- **已完成预处理清单**：校验成功后保持 `dataset.json` 字节不变，避免使已有权重的来源哈希失效；已完成缓存损坏或原始内容改变则拒绝混用，请另建目录。
- **旧模型只有最佳权重**：可以依原规则预测，但缺少优化器和随机状态，不能精确续训。需另建训练任务；不会静默把它当作完整训练检查点。
- **旧预测没有输出哈希**：缺少可验证的完成证明，该病例重新预测。新版本中断预测可按病例校验跳过。
- 旧流程没有已完成步骤校验快照时，环境步骤可沿用；其余标记成功的步骤保留产物并阻止自动续跑，不会静默重跑。未完成步骤仍按上述策略恢复。不把旧日志里的百分比当完成证明。

## 文件和并发保护

预处理逐病例写 `.resume/<病例>.json`，`preprocess-report.json` 逐例更新，只有全部完成才发布 `dataset.json`。预测分别原子写入 NIfTI 和网格，最后记录两者哈希；恢复时校验该完成记录；任一缺失/哈希错误会重新预测该例。文件使用临时文件和原子替换，强制终止留下的临时文件不算成功。

训练 `.last.pt` 是轮次提交点，其中保留最佳权重的原始字节；恢复会修复未写完的最佳权重导出和历史文件，保持血池 LSTM 编码器哈希一致。坏检查点会明确报错，不静默初始化模型。

新流程成功步骤记录输入/输出哈希，恢复时检测修改、新增、缺失文件。大数据目录校验可能耗时。数据、配置、划分、模型来源不符会停止，避免混合不同实验。

一个 runtime 一个流程；预处理、训练、预测输出另外加内核文件锁。Linux 子进程继承 runtime 锁，多卡子进程也继承模型输出锁。主进程被单独 SIGKILL 后，存活子进程仍持锁；恢复会拒绝重复写入，`--stop` 按本任务记录的启动身份停止存活进程。不要仅凭某个同名 Python PID 操作进程。

`attempts/` 保存每次恢复前的计划、状态和回执，日志追加；短步骤的旧目录保留。服务器重启或断电不能保证正在写入的数据落盘，但未完成产物不会被当作可直接消费的结果。磁盘不足、损坏检查点、环境安装失败、数据来源变化需修复后再恢复，不无限重试。

## 独立 Python 入口

独立入口可显式提供原输出目录；不依赖服务器工作流：

```bash
python preprocess.py --input /原始数据 --output /原预处理目录 --resume
python train.py --prepared /缓存 --output /原模型目录 --config configs/chd.yaml --mode train --device cuda --resume
python predict.py --prepared /缓存 --models /模型目录 --output /原预测目录 --device cuda --resume
python -m chd_ct.imagechd.test --prepared /缓存 --models /模型目录 --output /原测试目录 --device cuda --resume
```

参数须与原运行一致（例如原预处理用了 `--size 96`，恢复也需带上）。服务器分步脚本中新任务会创建新结果目录；要恢复旧训练/预测流程，应使用 `start_server.sh --resume-job`，不能仅给新任务加 `--resume` 就期待自动找到旧权重。

## 0.13.0 推理与 CPU 尾部恢复

测试/预测内部区分 GPU 计算和 CPU 后处理，原 workflow 的步骤编号、模型目录和训练检查点不变。GPU 计算完成后，状态暂为 `pending_cpu`；所有所选 GPU 工作结束后释放卡，再执行 CPU 尾部。续跑有效的 GPU 中间结果无需重新拿卡；哈希不匹配会重新计算需要的病例，来源或范围改变仍拒绝混用。

新增 CPU 病例 worker 和 GPU 推理 worker 继承输出/runtime 锁，登记 PID 身份，停止和更新会发现孤儿子进程。不能删除锁文件强行重启。预处理资源记录存步骤输出，不修改已完成的科学缓存清单。训练原有调优和恢复契约保持原样。
## 续跑校验读取优化（0.16.0）

面板 `r` 和 `--resume-job`（包括追加步骤）会把所有已完成步骤的快照合并校验。同一次操作中，同一规范路径的文件只完整读取、计算 SHA256 一次；共享目录的清单也合并扫描，结束前再检查文件集合与状态。仍然检查完整内容，不以文件大小或修改时间代替首次哈希，不跳过原始数据、缓存或权重。旧快照和旧任务目录直接兼容，无需重跑。

读取线程在校验内部自动选择，不新增步骤、不使用 GPU、不改变训练 CPU 调优：

- 采样约 0.2 秒，采用进程可用 CPU（affinity/cgroup）、当前空闲比例、可用内存及文件数量。
- 识别 Linux 实际挂载与块设备：网络存储最多 4 线程，SSD/内存盘最多 8，机械盘 1，无法识别时最多 2；混合来源取保守上限，不按目录名字猜测 NAS。
- 总读取量少于 32 MiB 时使用 1 线程。每线程按 4 MiB 分块，限制同时打开和排队的文件数；不会按整机 256 核启动 256 个读线程。它是有界启发式选择，不是吞吐实测最优。

每秒显示校验状态。扫描时报告扫描项数；读取时显示进度条、唯一文件数、已读/总 MiB、平均速度和**读取阶段**估算剩余时间。末尾的“复核文件状态”另行显示，只有全部检查通过才报告“校验通过”及保留步骤。多个步骤共享文件的读取量只统计一次，不夸大总量。小文件可能在两次刷新之间完成。

校验是只读操作，不改原产物的内容和修改时间；不保存跨运行的哈希缓存。检测到内容不匹配、快照冲突、新增/缺失文件或校验期间可见的状态变化即拒绝续跑。Ctrl+C 取消本次校验并清理读取线程后返回面板，不提交任务；若网络文件系统调用阻塞，需要等该调用返回，不能保证瞬间退出。校验不构成外部程序可写文件的原子快照，校验期间应保持输入和产物稳定。

独立合成验收见大 project 的 `server-resource-smoke/check_resume.py`，无需 ML 依赖或 GPU。步骤运行完成后生成快照的既有逻辑、结果只读查询以及训练调优不在本次改动范围。
