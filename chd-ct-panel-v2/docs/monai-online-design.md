# STU-Net MONAI 在线数据方案

状态：研发方案，尚未实现 MONAI 后端。

长期分支为 `chd-stunet-monai`，作为 main 之外维护的 MONAI 版本。沿用 `chd-ct-panel-v2` 工程及命令行入口，在本分支开发和验收。合并 main 单独审查。本次方案不包含真实病例编号、统计、路径或测试结果。

## 目标和数据位置

训练读取原始影像与标签，通过 MONAI 组织确定性处理及内存缓存。预处理数组、前景坐标和强度候选样本保存在 RAM；多进程共享使用有归属登记的系统共享内存，进程退出后释放。工作目录不写重采样 CT、标签、Blosc2、NumPy 或属性数组副本，不使用磁盘持久化缓存。

原始数据继续只读；数据专用挂载目录只保存数据集。每次准备、训练和预测拥有独立 workspace 运行目录。磁盘保留可复核的小型数据清单、每折计划、来源摘要、运行配置、冻结代码、必要日志及可续跑检查点。病例清单和数据分析内容均属于本机运行记录。

检查点只保存模型、优化器、scaler、学习率状态、已完成进度和随机状态，不序列化影像缓存。正常训练保留最新完整恢复状态及最佳模型；原子提交时需要临时文件，提交完成后精简。短测结束自动释放全部影像缓存及临时模型文件，只保留获准范围内的必要日志。

## 采用方式与依据

选择 `CacheDataset` 加受控共享内存，缓存非随机变换，随机取块与增强使用原训练采样协议。MONAI 的 `cache_num`、`cache_rate` 和运行时缓存容器为适配入口。容器传递共享数据的引用和小型元数据，禁止通过代理队列反复复制整个病例。

现有供数使用 spawn。MONAI 官方记录了 `SmartCacheDataset` 对 spawn、部分 DDP 启动方式及持久 worker 的限制；其按缓存子集训练的语义也需要独立适配。本方案保持完整训练名单的采样规则。

内存容纳完整活动折时，缓存该折所需数据；内存受限时，只缓存预算允许的病例，其他病例仍执行同一在线变换。缓存分配顺序不改变抽样名单、概率、前景比例或训练步数。完全在线计算的未命中开销必须计入验收。

依据为 [MONAI CacheDataset 与运行时缓存](https://monai.readthedocs.io/en/stable/data.html#cachedataset)、[MONAI SmartCacheDataset 的限制](https://monai.readthedocs.io/en/stable/data.html#smartcachedataset)和本项目现有 V2 资源、供数及恢复实现。CacheDataset 负责缓存确定性变换；项目适配层负责容量、生命周期和原算法接口。

## 科学方法与旧任务

保留 STU-Net-S 网络、权重解释、七结构输出、忽略标签、部分监督损失和深监督语义。训练轮数、batch、patch、每轮尝试次数及验证预算继续读取已有配置，不因更换框架自动改变。

将现有数值处理整理为可在内存中调用的共同实现，并封装为 MONAI `Transform`，使它能参与确定性缓存。影像非零裁剪、先归一化后重采样、插值阶数、标签安全处理和前景位置规则均沿用当前方法。继续采用作者间距来源与衍生 affine 校验，避免只根据文件头推断空间信息。

三折保留独立的 train、validation、test 角色和拟合参数。准备阶段扫描原始数据，候选样本只驻留 RAM，分别拟合每折计划后释放候选样本。活动折缓存的身份包括原始来源、方法版本、当前折、拟合计划和数组格式；不同折的缓存内容分别核验。换折按对应计划构建内存缓存。验证、测试和缺标注辅助病例不进入主训练集统计拟合。

旧训练继续通过原冻结代码和原输入恢复，原目录不自动转换。MONAI 后端产生新的数据和代码合同；本方案不承诺直接继承旧优化器进度并获得同一随机轨迹。已有权重的预测保留原模型记录的预处理解释；新 MONAI 模型的预测须读取自己的计划并完成来源兼容审查。

| `run.py`、`smoke.py` | 继续作为业务与独立短测入口 |

## CPU 与内存加速

1. 延用 V2 的有效 CPU、实时 RAM、cgroup 与独立 I/O 准入。阶段 CPU/RAM 采用 80% 预算，保留阶段可用 RAM 的 20% 且至少 4 GiB。预算需要包含缓存、坐标、并行数值变换、worker、队列及传输副本。
2. 缓存可用量等于任务 RAM 预算减去模型主机状态、数值变换峰值、队列及传输预留。按各病例预计解压体积规划，构建完成后用实际字节数核验，不按压缩文件大小估计。
3. 一个 CPU 缓存管理者维护本次任务的内存引用，GPU rank 和供数进程复用数据；同一病例同一合同的并发构建去重。缓存以小型句柄传递，避免每张卡独立缓存整套数据。
4. 各缓存项只读，取出训练 patch 后显式复制该 patch，再执行随机增强，避免为每个 batch 深复制完整三维影像。随机结果不进入确定性缓存。
5. 当前批次需要的病例优先准备；其他病例的读取和变换利用剩余 CPU/RAM 并发推进。保留当前批次顺序，不通过跳过慢病例改变抽样。
6. 持久 worker 与预取槽共同准入。已有可传输批次时，只预取已就绪的下一序号；缓存管理者不占用正在等待缓存的同一供数执行池，避免互相等待。
7. 每秒核对真实内存压力。只回收没有存活使用者的缓存项；需要重组时先完成安全边界保存、停止本组供数进程，再减小缓存和 worker 预算。缩小后的预算跨 GPU 重组保留。
8. 同时检查系统共享内存容量。共享区域使用 nonce、进程出生身份和引用登记；只有本任务创建且已无使用者的区域可以回收。共享内存容量不足时明确等待或停止准入，不写磁盘影像替代缓存。

## GPU 加速和资源变化

延用当前全局 batch 合同，默认最多自动选择两张获准 GPU。batch=4 时，单卡分配 4，两卡各分配 2；不改变总 batch。选择依据是实际尺寸容量与稳态吞吐，卡数和显存占用不作为提速证据。

显存余量按 V2 保留至少 4 GiB 或总显存的 10%，采用较大者。只向 GPU 传输当前 patch，使用有界 pinned memory、异步传输和 CUDA 事件；不把整套影像放到显存。缓存管理者在 GPU 等待期间保持小型元数据状态，正式大缓存分配与实际计算阶段准入关联。

AMP、梯度归约及不均分 batch 处理沿用现有实现。编译默认按现有已核验配置运行；新增编译优化必须单独验证输出、梯度、随机性和冷启动代价。MONAI 的延迟重采样可能改变插值执行方式，默认保持现有数值顺序。

外部进程占卡、暂时无卡和已分类的资源不足使用可恢复状态处理：安全保存进度，重新选择 GPU 或减少卡数；无卡时按配置等待并输出心跳。数据错误、非法标签、来源变化和代码合同不匹配直接停止。GPU 组重建尽量保留 CPU 缓存管理者，避免因换卡丢失可复用的内存数据。输入合同与全局 batch 保持不变。

## 断点和日志

检查点保存已消费的采样游标、全局 slot 随机状态、模型、优化器、scaler 和训练进度。预取内容不作为已训练数据；恢复后可重算尚未消费的批次。内存缓存状态不进入模型科学身份；程序重启可重建缓存，同一拓扑的采样与数值一致性须实测，跨 GPU 拓扑不承诺逐位相同。

日志分别记录读取、解压、数值变换、缓存命中/未命中、缓存字节数、缓存释放、取块、随机增强、队列等待、主机到显卡传输、计算、验证及检查点写入。输出实际 worker、线程、队列深度和 GPU 布局。低吞吐需要给出当前阶段和等待原因，避免只有笼统的“运行中”。

## 发布与数据边界

- GitHub 只提交代码、通用配置、依赖声明和通用文档。真实影像、标签、数组、权重、检查点、病例清单、实际路径、来源哈希、病例统计和本机验收报告均不作为公开代码上传。
- 除 `.gitignore` 外，发布必须使用明确的代码白名单，核对待发布文件、扩展名、二进制内容和文本敏感信息；不使用全目录添加或把运行结果混入代码包。
- 默认路径使用已有通用模板，机器路径和实际病例信息只存本机配置及 workspace。公开测试使用通用样本名称。
- 新分支的 update 必须显式读取 `chd-stunet-monai`，防止默认读取 main 覆盖 MONAI 版本；更新来源分支及固定提交写入日志。
- main 的已发布任务保持自己的冻结代码、配置和依赖。此分支的功能验收完成后，也需要单独决定是否合并 main。

## 验收和实施次序

先固定数据后端合同、依赖和准备阶段，再接入无文件写出的变换与共享缓存，随后接入现有训练、恢复和预测，最后检查更新与发布入口。各部分调用相同业务实现，短测不维护另一份演示算法。

获准后仅选 1–2 个明确病例，执行有边界的真实依赖检查：对照原算法的完整数组与属性，检查标签、三折拟合来源、缓存身份、内存压力、进程占用、释放、恢复采样及必要的少量模型更新。分开报告冷启动和稳态，固定 patch、batch、采样工作量后比较吞吐、GPU 等待和峰值内存。

短测生成前单独说明病例、步骤、目录、文件数、容量和清理范围并取得授权；本方案不启动安装、影像处理或模型训练。测试结束清理缓存、暂存和临时模型文件，必要日志留在本机。实际速度、是否能缓存完整活动折及 Linux/NCCL 行为在测试后报告，不用预算推断性能。
