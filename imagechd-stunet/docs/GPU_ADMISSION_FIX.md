# 训练阶段显卡状态复查（0.5.2）

## 故障与证据边界

0.5.1在容量短测后只调用一次admit，任一卡利用率超过10%就抛出
ResourceAdmissionError；该检查位于原容量恢复分支外，会直接结束任务。
用户提供的四卡32%/100%错误对应这一分支，原因记录是利用率而非计算PID或显存不足。

NVIDIA说明GPU利用率统计的是上一采样周期，周期依产品约1/6至1秒：
[nvidia-smi官方说明](https://docs.nvidia.com/deploy/nvidia-smi/index.html#utilization)。
因此刚结束短测的历史采样是一种可重现解释；仅凭该错误不能断言服务器没有真实竞争进程。
本补丁使用合成监测序列重放控制故障，没有连接服务器或运行GPU/真实CT。

## 当前处理

1. 卡组仍来自GPUFleet的获准可见范围、真实空闲采样和已核验keeper。
   admit保留原可见性、外部计算PID、利用率10%和显存门槛，拒绝项附reason_code及原监测行。
2. settled_admit用于容量短测前、短测后及正式训练启动前；旧rank均须实际退出。
   首次全部通过可继续。若仅有利用率/显存释放瞬态拒绝，则在10秒窗口内按1秒间隔复查，
   发生过拒绝后必须有两次连续整组通过；超窗样本不能放行。
   单次nvidia-smi查询受其原有超时约束，查询耗时计入窗口，不保证操作系统能在10秒内返回。
3. 外部PID/可见性失效立即阻止放行；ready_group重新采样，优先只释放硬拒绝卡的本任务keeper。
   同一行程里其他卡仅有瞬态读数时，继续复查这些卡，不能整批释放。
   持续未通过的卡也不强行使用，保留其他安全卡；全组不可用则等待GPUFleet发现新的兼容空闲组。
   实际释放卡保留原600秒冷却策略，其他兼容空闲卡不受此限制。keeper不是管理员级独占预约。
4. 容量阶段卡组变化会丢弃该次短测、重新计算CPU/RAM/batch并验证新组，最多3次重建；
   正式启动前连续准入变化同样最多3次重建。第四次仍失败明确停止并保留日志。
   等待空闲卡是资源排队，与无限重试模型错误不同；未知错误、监测失败和用户中断直接传播。
5. 不修改损失、优化器、250轮×250训练尝试/50验证、预处理或依赖；不降低门槛、不结束外部进程。
   新卡仍只在完整epoch检查点边界加入，旧冻结任务不热修。

## 更新和定位

保持原runtime，更新并重新打开面板，核对0.5.2；新建训练任务，选择已完成且兼容的预处理。
本补丁没有更改七文件准备身份或依赖规格，环境未另行变化时无需重跑预处理。
原失败训练保留冻结源码和日志；不能仅用旧任务重启来加载新版调度。

日志中心l的训练步骤日志显示等待/重选；workspace/diagnostics/events/*.jsonl记录
gpu.admission_sample、gpu.admission_timeout、gpu.admission_reselect、capacity.admission_changed，
包括阶段上下文、UUID、PID/显存/利用率原拒绝行、阈值、耗时和次数。
GPUFleet原gpu.sample提供完整周期监测。需要排查时通过z导出该任务诊断包。

验证见[GPU_ADMISSION_VALIDATION.json](GPU_ADMISSION_VALIDATION.json)及
[test_gpu_admission.py](../tests/test_gpu_admission.py)。这些是控制流程证据，不是目标服务器吞吐或训练质量验收。
